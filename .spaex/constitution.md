- **MUST NOT** commit key material (SSH private keys, OAuth tokens, API keys, passwords, or encrypted-at-rest secret blobs) to git in any form, in the harness repo or any repo consuming its harness, anywhere in repository history. Repos carry only references to identities, such as `identity: work-github`. Encrypted secrets committed to git are effectively permanent (rotation is not deletion, and harvest-now-decrypt-later remains a live threat), so plaintext must never enter repository history in any form. _[from `com.github.haexmas.atoms.spaex-constitution/no-secrets-in-git`]_

## SHOULD

- Consult graphify first when the task is to locate the correct domain artifact, and use `ast-grep` afterward to enumerate or validate structurally matching code, since `ast-grep` is a precision tool rather than the project's source of architectural truth. _[from `com.github.haexmas.atoms.ast-grep/ast-grep-structural-search`]_
- Use `ast-grep` (or its `sg` executable) instead of a broad regular expression or text replacement when a search or rewrite depends on code structure, such as matching a call shape, finding a declaration form, or changing a syntax pattern across several files. _[from `com.github.haexmas.atoms.ast-grep/ast-grep-structural-search`]_
- Keep modules and exports focused, preferring named exports for reusable library code and avoiding circular dependencies. _[from `com.github.haexmas.atoms.coding-guideline-javascript-typescript/javascript-typescript`]_
- Prefer const declarations and keep mutation local, using `let` when reassignment makes the state transition clearer. _[from `com.github.haexmas.atoms.coding-guideline-javascript-typescript/javascript-typescript`]_
- Prefer immutable transformations at shared boundaries while allowing simple local mutation where it is clearer and measurably avoids needless allocation, because readability and correct ownership of state matter more than a blanket immutability rule. _[from `com.github.haexmas.atoms.coding-guideline-javascript-typescript/javascript-typescript`]_
- Treat TypeScript's strict mode as the baseline for new or actively maintained TypeScript code. _[from `com.github.haexmas.atoms.coding-guideline-javascript-typescript/javascript-typescript`]_

- Keep type-level tests separate from runtime tests when the project needs to verify inference, assignability, or declaration output, since runtime tests cannot prove a compile-time contract and the compiler cannot prove runtime validation of external data. _[from `com.github.haexmas.atoms.coding-guideline-javascript-typescript/javascript-typescript-testing`]_
- Name a test after the behavior and the relevant condition rather than after the implementation method alone. _[from `com.github.haexmas.atoms.coding-guideline-javascript-typescript/javascript-typescript-testing`]_

- Test observable behavior and public contracts, including the important failure paths, rather than private implementation details, so that a refactor preserving the contract does not require rewriting the suite and a regression in promised behavior does fail a test. _[from `com.github.haexmas.atoms.coding-guideline-javascript-typescript/javascript-typescript-testing`, `com.github.haexmas.atoms.coding-guideline-rust/rust-testing`]_
- Choose the smallest correct implementation that fits the existing crate conventions. _[from `com.github.haexmas.atoms.coding-guideline-rust/rust`]_
- Keep public APIs narrow, and avoid exposing implementation details solely to work around a local borrow or lifetime problem. _[from `com.github.haexmas.atoms.coding-guideline-rust/rust`]_
- Prefer iterators and combinators where they make the transformation clearer, and an ordinary loop where it communicates control flow or error handling better, since idiomatic syntax is not a reason to make code harder to read. _[from `com.github.haexmas.atoms.coding-guideline-rust/rust`]_
- Prefer types that make invalid states unrepresentable, using enums for a closed set of states and `Option<T>` for an explicitly optional value. _[from `com.github.haexmas.atoms.coding-guideline-rust/rust`]_
- Respect ownership instead of fighting it: borrow when the callee does not need ownership, and return owned data when the result must outlive the input. _[from `com.github.haexmas.atoms.coding-guideline-rust/rust`]_
- Keep test helpers small and local to the tests that own them, reserving a shared fixture for a stable domain setup rather than for removing a few repeated lines. _[from `com.github.haexmas.atoms.coding-guideline-rust/rust-testing`]_
- Keep the test suite readable, fast enough to run often, and trustworthy when it passes, because a test suite is production code. _[from `com.github.haexmas.atoms.coding-guideline-rust/rust-testing`]_
- Make a test fixture satisfy the same contract as a real caller. _[from `com.github.haexmas.atoms.coding-guideline-rust/rust-testing`]_

- Follow a repository's existing documented structure, naming scheme, or size convention unless the task explicitly changes it, since these defaults are not a reason to reformat or reorganize an entire codebase. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- Give each file one primary reason to change, splitting it when it carries unrelated responsibilities, independent public concepts, different change owners, or tests that are difficult to isolate. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- Give each function one coherent responsibility at one level of abstraction, extracting a helper when it names a concept, makes a branch independently testable, or removes repeated logic rather than merely because the function crossed an arbitrary line count. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- Keep dependencies directed and understandable, avoiding circular imports, hidden global state, and a domain layer that knows about infrastructure details, and placing I/O, framework adapters, and process wiring at the edges when the architecture calls for that separation. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- Keep each change self-contained and easy to review, grouping production code, relevant tests, documentation, and configuration that describe the same behavior, and splitting independent refactors and unrelated cleanups into separate changes. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- Keep public module interfaces narrow and intentional, hiding implementation details behind the smallest stable API the callers need. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- Keep related tests close to the behavior they verify according to the language and repository convention, and treat a module split as incomplete while its tests, documentation, fixtures, and call sites are left misleadingly behind. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- Keep side effects at visible boundaries so that pure calculations and decisions are easy to test without a database, network, filesystem, clock, or global mutable state. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- Name code after its domain meaning and behavior, preferring a clear name over a comment that explains an otherwise opaque `data`, `helper`, or `process` function. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- Organize code around cohesive domain or feature boundaries where the codebase supports it. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- Prefer a change that clearly improves maintainability and correctness over theoretical perfection, and when a design is uncertain make the smallest reversible change that provides evidence about the next decision. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- Prefer early returns or named helpers when they make the main path easier to follow, reducing nesting without scattering one simple operation across many microscopic functions. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- Refactor repeated behavior when the shared rule is real and the abstraction makes both callers clearer, keeping the abstraction close to the domain that owns it. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- Separate broad formatting or mechanical refactors from behavior changes when possible, because mixed diffs make review, debugging, rollback, and blame less reliable. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- Treat a change of about 100 net lines as a useful review-size warning and a change approaching 1000 lines as a strong prompt to split the work or agree on the larger change in advance, identifying generated code, mechanical renames, and required migrations as legitimate exceptions. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- Use smaller soft thresholds as prompts for review rather than automatic failures, giving a deliberate look to a function or method beyond roughly 40–60 lines or nesting deeper than roughly three levels to decide whether it is still one coherent unit or hides distinct responsibilities worth naming and separating. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- Preserve in the resulting context map, where available, the task intent and token budget, the selected files and symbols, the relevant edge or call relationship, source locations for every claim, and an explicit truncation or failed-consultation note. _[from `com.github.haexmas.atoms.graphify-first-authoring/graphify-context-map`]_

## SHOULD_NOT

- Use `any` where a precise type, a generic, or `unknown` followed by explicit narrowing would do, and keep every untyped escape hatch local with an explanation of why it is necessary. _[from `com.github.haexmas.atoms.coding-guideline-javascript-typescript/javascript-typescript`]_
- Weaken a production invariant merely to make a test convenient. _[from `com.github.haexmas.atoms.coding-guideline-rust/rust-testing`]_
- Do not abstract two things merely because they look similar, but first establish that they share behavior, ownership, change reason, and invariants, since a small amount of local duplication is preferable to a premature generic abstraction that couples unrelated callers. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- Do not create folders only for superficial symmetry, such as putting every small class, interface, or helper in its own folder. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- Do not enforce a universal maximum line count for functions, files, or pull requests, because domain complexity, cohesion, control flow, and the number of reasons to change are more meaningful signals. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- Do not let a generic utility module become a dumping ground. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- Do not re-export everything or create pass-through modules that add no boundary. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- Do not split a file solely to make it shorter. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- Do not use comments to narrate code that could be made clear through structure and naming. _[from `com.github.haexmas.atoms.general-coding/general-coding`]_
- Over-extract fewer than five purely structural lines such as setup, error wrapping, or adapter boilerplate. _[from `com.github.haexmas.atoms.graphify-first-authoring/graphify-first-authoring`]_
- Treat the graphify-first rule as a mandate to rewrite duplicates already in the codebase, as a requirement that the graph be complete or perfect, or as a replacement for human code review. _[from `com.github.haexmas.atoms.graphify-first-authoring/graphify-first-authoring`]_
